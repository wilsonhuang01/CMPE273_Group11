Suggested dependency order

W01 → W02/W03 → W04 → W05 → W06 → W07. W08 is an optional upload enhancement. W09 and W10 follow W07; W11 closes the local milestone. W12 → W13 → W14 start after the AWS deployment handoff. Agree on the interface in W02 while infrastructure work proceeds in parallel.

W01–W14 are stable website action identifiers. Local milestone: bundled-example submission, truthful task status, results, verified downloads and recorded fallback.

Application boundary

Browser → same-origin Python web API → existing coordinator gRPC → existing optimizer pipeline. The coordinator owns durable task execution, verification, worker recovery and final selection. The web API adapts browser requests and task-scoped evidence. Static assets live in web/; the proposed API package lives in src/compiler_optimizer/web/. These locations and web configuration names are proposed work, not existing commands or files.

Local mode uses 127.0.0.1:50052. Remote mode changes server-side endpoint, TLS, secret and connectivity configuration; browser URLs remain relative. AWS integration may also require application/schema reconciliation when the deployment branch lands. Live task history and artifacts stay in their original environment.

Existing local baseline commands

./project names the launcher executable inside the root directory. These commands validate the existing backend; they do not start the planned website.

# Terminal 1 — Docker running; starts/checks dependencies
./project serve

# Terminal 2 — use a fresh request filename for a deliberate new task
./project client submit examples/sum-array --request-file var/client/web-demo-request.json --wait
./project client status TASK_ID
./project client download TASK_ID --output var/client/web-demo-results

Replace TASK_ID with the printed ID; download output must not already exist. Reuse the same request file to retry the same submission. The proposed ./project web command is delivered by W10 and is not available merely by adding this backlog.
